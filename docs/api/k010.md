# K0.1.0 API contracts

The local API exposes [Swagger UI](http://127.0.0.1:8080/docs) and
[OpenAPI JSON](http://127.0.0.1:8080/openapi.json). The inventory contains
39 operations across 34 paths. Resource IDs are UUIDs.

Use the session cookie returned by login. For authenticated writes, send
the returned `csrf_token` as `X-CSRF-Token`. Pagination uses `offset`,
`limit`, and `next_offset` on list resources. Authorization filters items
before pagination.

## Workflow details

- Imports take `application/json` up to 1 MiB. Issue batches use
  `kind: "issue-events"` and an `events` array. Conversation batches use
  `kind: "conversation-notes"` and a `notes` array. Both use `provider` and
  entries with source IDs, authors, event timestamps, references, exact text,
  event types, and optional related IDs and access policy. The API returns
  202 and a job ID. Use `Idempotency-Key` to repeat identical bytes safely.
  [Synthetic issue example](../../backend/tests/fixtures/issues.json) ·
  [Synthetic conversation example](../../backend/tests/fixtures/conversations.json)
- Agent jobs take `task`, `audience` and optional `source_ids`. Create the
  draft using the succeeded `agent_job_id`. A correction includes
  `draft_id`, `expected_revision`, `content` and `reason`. Approve using
  `expected_revision` and the reviewed `rubric`. To make a version
  eligible for readiness, include `critical_gap_review`.
- The critical-gap review confirms all draft `source_revision_ids` in
  `reviewed_source_revision_ids`. Its `claims` list records one
  `claim_revision_id`, `classification`, `disposition` and `rationale`
  for every current draft claim, including rejected claims. Classifications
  are `prerequisite`, `blocker`, `approval`, `ownership` and `non_critical`.
  Critical items can be `blocking`, `unverified` or `resolved`.
  Resolution requires a resolved claim with supporting evidence. Use
  `non_blocking` with `non_critical` for explicitly reviewed non-critical
  items. Use `additional_gaps` to record a blocking or unverified condition
  missed by the model, with a `source_revision_id` from the draft snapshot.
- Trace takes optional `version_id`. An assigned recipient supplies the
  approved version ID. The trace separates decision status, exact evidence
  and chronology, relationships, and unresolved items. Current draft trace
  requires an editor role and visible evidence.
- The version response includes the approved rubric ID. A readiness attempt
  takes an `answers` object keyed by `action`, `prerequisites`, `evidence`
  and `escalation` with zero-based choices. Optional fields are
  `client_attempt_id` and `explanation`. Repeating the same attempt key and
  answers returns the existing record. Receipt has no request body and
  repeats return the same timestamp.
- Confirmed blockers give `blocked_by_project_gap`. Versions without a
  review retain any existing prerequisite or blocker gate. Otherwise a
  missing or unverified review gives `stale_or_requires_review` with the
  `critical_gap_review_required` gate. Existing approved versions can
  still serve rehearsals and receipts. Reapprove a current draft with a
  complete review to make it eligible for readiness. Changes to reviewed
  claims or source revisions stale the prior version.
- Errors use `code`, `message`, and `request_id`. Responses include
  `X-Request-ID`. Expect 401 for missing authentication, 403 for a denied
  operation, 404 for an invisible resource, 409 for stale state or a
  conflicting retry, 413 for an oversized import, 415 for a media-type
  mismatch, 422 for invalid input and 503 for unavailable dependencies.
  If the database connection or Redis is unavailable during sign-in, login
  returns 503 with a request ID and does not issue a session cookie. Check
  `/health/ready` to distinguish process liveness from dependency readiness.
### Personal onboarding

- `POST /api/v1/auth/register` creates an account without memberships. Sign in through the existing session endpoint afterward.
- `POST /api/v1/workspaces` creates a workspace and makes the authenticated creator its administrator in the same transaction.
- `GET /api/v1/projects/{project_id}/recipients` lists active assigned recipients for project editors. Workspace administrators can `POST` an existing workspace member's email to the same route to assign them as recipient.
- `POST /api/v1/projects/{project_id}/invitations` returns a short-lived one-time code for the specified account email. Share it privately. `POST /api/v1/invitations/redeem` consumes it for the signed-in matching account. Existing roles are preserved.
- Draft responses include an authorized `source_snapshot` for display. Approval and citation writes continue to use the exact revision identifiers.

### Evidence provenance

Public issue comparison returns the official issue body and metadata, retrieval
time, state reason, closure time, assignees and a snapshot fingerprint. It does
not persist the fetched issue or
change the provenance of any local citation. Citation offsets still refer to
the stored revision, including when the local text is a manually entered summary.
An exact match establishes the span. Reviewers separately confirm that the
excerpt supports the meaning of the claim.

Agent-run failures use sanitized stage codes such as
`provider_quota_or_rate_limit`, `provider_authentication_failed`,
`provider_model_unavailable`, `provider_invalid_request` and
`provider_temporarily_unavailable`. Quota, authentication, model and invalid
request failures are not retried. Transient 5xx responses and invalid structured
output retain the configured bounded attempt limit.
